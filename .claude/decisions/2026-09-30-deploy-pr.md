# Deploy PRs: a release proposes itself to each GitOps overlay, one merge at a time

**Status:** proposed (2026-09-30)

## Context

Consumers deploy with Flux: an `ImagePolicy` watches the registry and an
`ImageUpdateAutomation` commits the newest matching tag straight to the branch
the cluster reads. For acceptance and production that makes every release a
deployment with no review, and "what runs in prd" whatever the last automation
commit said. The ask: no automation writing to acc and prd, a pull request per
environment as soon as a stable version exists, and prd only ever getting what
acc has run.

Diatreme is the one component that knows the version, the tag and the exact
images at the moment they are released.

## Options considered

1. **Renovate in the consumer**, polling the registry on a schedule or started
   after the release. It owns PR lifecycle well, but it learns about the
   release second-hand (a registry scan, needing its own registry credentials),
   cannot express "prd gets what acc merged", and is one more tool, config and
   token per repository.
2. **Image automation pushing to a side branch**, plus a workflow that opens a
   PR from it. Keeps Flux as the scanner, but the automation force-updates that
   branch under an open PR, and promotion order is again not expressible.
3. **Diatreme opens the PR** after the release, and a new mode opens the next
   overlay's PR when one merges.

## Decision

Option 3.

- `deploy-pr-targets` maps an environment to overlay directories in promotion
  order. `mode: release` opens a PR for the first; `mode: deploy-promote`, on
  `pull_request` `closed`, opens the next when a deploy PR merged.
- What is deployed is the image list `Promote images` actually promoted (its new
  `repositories` output), not a fifth derivation from the bake file.
- What is promoted onwards is read from the merged overlay: its tags at the
  merge commit against the first parent. Not from the PR body or branch name, so
  a reviewer's edit on the branch is what travels, and nothing the PR did not
  move is carried along.
- One branch per overlay and tag, `<prefix>/<overlay>/<tag>`, committed with the
  contents API on a branch created at the base tip. An open PR's branch is never
  reset: GitHub marks a PR merged the moment its head points at a commit the
  base contains.
- Only the value on the `newTag:` line changes. The file is not re-serialised.
- A push that changes nothing but the overlays is refused in release mode
  before versioning, and a PR that changes nothing but the overlays skips the
  ci image build.

## Rationale

- The release is the event. Opening the PR from it is immediate, exact about
  the tag, and needs no registry access beyond what the release already had.
- Reading the merge rather than trusting metadata means the chain cannot drift
  from what the cluster actually got.
- A line edit keeps diffs to one line per image and keeps comments, such as the
  Flux `$imagepolicy` markers consumers still have while they migrate.
- Refusing a deploy merge instead of versioning it breaks the loop the setup
  would otherwise create (merge, release, new deploy PR, merge, ...) even when a
  consumer forgets `paths-ignore`.

## Consequences

- A new mode and three inputs are frozen surface from the first release.
- Deploy PRs need an App token: a PR opened with `GITHUB_TOKEN` starts no
  workflow, so required checks never report.
- The consumer carries three workflow changes (the overlays in push
  `paths-ignore`, `closed` in the pull request types, the mode expression), and
  must remove the image automation for those overlays itself.
- Overlays in another repository, Helm values and digests are out of scope.
- `sort -V` decides "newer" between tags. It orders a stable version before its
  own prereleases, which only matters if one overlay's chain mixes channels.
